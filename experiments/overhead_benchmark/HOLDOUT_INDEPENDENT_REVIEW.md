## 汇总脚本审阅

`analyze_overhead_holdout.py` 会在汇总前要求 20 个 case、60 个 memory profile 齐全；复核执行器/包装器哈希、配置与源码哈希、逐轮完整性、通信轨迹、同种子初态、Python/NumPy/BLAS签名、旧种子不重叠及 oracle 总数。它从原始配对数据重算成本比，并核对现成汇总中的中位数、范围和胜出数；耗时/流量加总、重算比例和持久数组也有逐项交叉检查。新报告对 0.16 结论的解释准确：4/5 严格小于 1，范围跨过 1，且强调该胜出数不代表稳健余量。输出采用独占创建，能避免覆盖已有报告文件。

范围澄清：分析器对每个新 case 的 environment 文件逐项比较 Python、NumPy 及 BLAS 内部实现/版本/线程数；该环境逐 case 对比已实现。它没有把新旧性能 case 的耗时做同 scale 的直接自动对比；历史 0.16 是否“三个均慢”由我单独从旧原始 JSON 复核，见上文。这不混入本轮新种子的配对统计。

`integrity.json` 的 `result_hashes` 先于最终 CSV 和 Markdown 生成，未覆盖这些最终产物。报告已说明由主 AI 在本审阅定稿后另生成 `delivery_hashes.json`，纳入报告、审阅记录、汇总文件、原始结果及执行器等交付文件，并独立逐项验证；清单本身不递归列入。

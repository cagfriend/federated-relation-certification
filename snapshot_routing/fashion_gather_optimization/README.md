# D 的特征收集优化与新种子确认

先定位 `features[ids]` 的分配和行收集成本，再验证改进能否降低完整头部耗时。配置沿用 E55 的 Fashion-MNIST M4096、K10、六个客户端、200 轮、相同冻结特征和学生更新预算。

## 阶段一 · 在真实刷新请求上筛选

旧 D 在强非 IID 的 3101、3102、3103 上各跑一次审计，捕获每轮每客户端的真实刷新索引、冻结特征和教师参数。旧 D 的硬关系逐轮对照全量 B 打分。用同一批请求重放三种行收集方式。

- 旧 D 使用 `features[ids]`。
- `take_allocate` 使用 `np.take` 为每次调用分配输出。
- `take_reuse` 使用 `np.take(..., out=...)`，在当前串行引擎的六个客户端间复用同一块连续缓冲区。该缓冲区每进程按需分配一次，正式配置容量 8 MiB。首次分配计入计时。

两种 `take` 均使用 `axis=0, mode='clip'`。审计要求端点索引有序、唯一且在范围内，收集矩阵逐元素相同且赢家一致。每种方式在每格的六个重放块中各出现六次，三种顺序位置各出现两次。报告行收集和收集加打分的耗时，按宽度以及重算比例分层。收集加打分包含偏置和 argmax。各工具运行次序及不合格尝试保留。

候选在至少两个种子上将每格六块平均「收集加打分」耗时降低至少 10% 才能进入确认。两者均达标时，先比较达标种子数，再比较三个种子的平均省时百分比，完全并列时选额外常驻缓冲区较小的分配版。程序封存候选；无候选达到门槛时结束并生成筛选报告。

## 阶段二 · 用新种子确认完整头部

固定候选后才准备并测量 3111、3112、3113，每个种子各跑 IID 和 Dirichlet α=0.1。B、旧 D、改进 D 在每格做六个无插桩计时块，三种方法的六种顺序各用一次，共 108 个有效计时进程。另有 18 个独立审计进程。缓冲区分配、初始化和全部头部轮次计时。计时进程用摘要与独立审计对照。

- 审计逐轮核对硬关系、聚合计数、学生目标与顺序、头参数、质量评估和应用层字节。旧 D 与改进 D 还须逐轮匹配重算端点和认证缓存。
- 强非 IID 至少两个种子达到改进 D 对旧 D 完整头部均值省时 ≥3%，且至少赢 5/6 个配对。IID 每个种子的平均增时均低于 3%。技术重复用于评估计时波动。
- 对全量 B 单列结果，按各划分报告达到同一实用门槛的种子数。记录缓冲区逻辑容量、认证缓存和进程峰值。
- 正式模式沿用上一轮电源和休眠检查，不合格时每块整体补测一次。备选确认流程结束前若仍缺有效块，报告标为证据不足。

## 本地运行

在仓库根目录执行，数据目录内放四份官方 Fashion-MNIST IDX gzip 文件。正式模式默认使用上一次归因实验的已准备缓存，如需指定其他位置可传 `--development-cache`。无默认缓存时从官方数据准备。用于确认的新种子会从官方数据重新准备。

```powershell
python -B -m snapshot_routing.fashion_gather_optimization.run --preset full --data-dir $fashionData
```

短测使用真实数据的缩小配置和三轮训练，并固定走复用候选来检查第二阶段。短测的计时结果只用于流程检查。

```powershell
python -B -m snapshot_routing.fashion_gather_optimization.run --preset smoke --data-dir $fashionData
```

默认输出 `outputs/fashion_gather_optimization_<preset>`，可用 `--output` 指定。中断后在原命令追加 `--resume`，已封存的确认配对保留，未封存的整块重跑。

筛选报告为 `screening/report.md`，各宽度和刷新比例的记录在 `screening/strata.csv`。若进入确认，使用 `confirmation/report.md` 和 `confirmation/paired_blocks.csv`，缓冲区及进程峰值见 `confirmation/runs.csv`。过程记录、选定候选与完成状态均有 SHA-256 回执。

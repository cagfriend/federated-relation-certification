# Demand 只在聚合者重建请求

上一轮的共享日程 Demand 在 STL-10 M4096 每 200 轮净省 528,205 应用层字节，但六端合计补算 6,000 次同伴请求，完整头部耗时相对显式 Demand 增加 5.19%–10.54%。本实验检验只在聚合者重建是否保留计时优势，同时减少请求上传。

## 冻结设计

- 沿用上一轮 12 组 STL-10 M4096 配置。种子 2021–2026 各含 IID 和 Dirichlet α=0.1，六个固定客户端，冻结表示，200 轮，每轮两批学生公共边。复用上一轮已封存的实验输入、选定模型、公共样本库和 B、D、显式 Demand 审计。所有计时方法在本轮重新配对运行。
- **D** 提供全图对照。**显式 Demand** 每轮上传请求并下发并集位图。**仅聚合者重建版** 使用同一日程注册，在每轮由聚合者重建其余五端的有序请求，仍序列化并向远端广播旧版并集位图。其他客户端独立生成自己的学生边顺序。每格预计补算 1,000 次同伴请求，固定请求上传去除 225,000 字节。
- 仍按六种排列各计一次，12 格共 72 个配对块、216 次有效无插桩计时。12 个新增审计单独检查聚合者重建顺序和远端收到的位图，并比对上一轮的投票、聚合计数、学生目标、损失、更新参数和评估。独立审计记录聚合者重建耗时。无插桩计时包含初始化、日程注册、逐轮重建和并集编解码。
- 通信按实际序列化包对账。净省字节为删除的请求上传减去新增的日程注册与握手回执，上下行分别核对。并集下发、投票、目标和逐轮控制消息均保持分项字节一致。报告消息数、完整头部墙钟、协调时间和各阶段时间。

## 判据

相对显式 Demand，要求平均完整头部增时不超过 3%，且六个块至少四个满足同一限制。相对 D，单独报告总字节，并检验平均完整头部省时至少 3% 且至少赢 4/6 块。IID 和强非 IID 分别汇总。重复块是技术重复。正式块使用上一轮的插电与休眠规则，不合格时整块补测一次。

运行范围为同版本 NumPy 采样器、固定成员和可靠串行内存消息。通信统计为应用层序列化字节。

## 本地运行

在仓库根目录执行。默认从本仓库的 `outputs/snapshot_routing_shared_schedule_demand_full` 读取上一轮已完成结果及其引用的本地缓存。移动过上一轮结果时通过 `--source` 指定其目录，并保留其原清单引用的 E42 目录及准备资产。

```powershell
python -B -m snapshot_routing.leader_schedule_demand.run --preset full
```

短测可用 `--preset smoke --source <已完成的共享日程合成短测目录>`，判据仅用于正式运行。正式运行接通电源。原命令加 `--resume` 继续已封存区块。

默认写入 `outputs/snapshot_routing_leader_schedule_demand_<preset>`。主结果为 `report.md`，通信对账见 `bytes.csv`，逐块与逐次计时见 `paired_blocks.csv`、`runs.csv`，独立重建诊断见 `reconstruction.csv`。

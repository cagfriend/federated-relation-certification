# Independent review: STL-10 setup and engine

Review date: 2026-11-01  
Scope: read-only inspection of `experiments/stl10_transfer/data.py`, `engine.py`, `design.py`, `PREREGISTRATION.md`, and the shared preparation/metric code they call. No source files were changed. I did not download data or run the experiment.

## Conclusion

I found no blocking mismatch in the reviewed data preparation or engine paths against the preregistered STL-10 setup. The source separation, STL-10 image layout conversion, 3×3 RGB averaging, label use, deterministic private partitioning, max-pool cache reuse, and head-timer boundary are supported by the implementation. The new curl fallback remains untested here; official MD5 checks are still applied before an archive is accepted.

## Evidence

- **Source identity and asset integrity:** `data.py` fixes the five official STL-10 asset MD5s and archive MD5 (`FILES`, `TARBALL_MD5`); `ensure_data` verifies the archive before extraction and each member afterward ([data.py](../../experiments/stl10_transfer/data.py#L14), [data.py](../../experiments/stl10_transfer/data.py#L74)). Extraction writes only the five basename-selected regular files to the intended directory. The urllib-to-curl fallback removes only this attempt's partial file and applies the same archive checksum afterward.
- **Prepared cache identity:** cache keys include preparation config, seed, partition, fixture status, source hashes, code identity, and dependency versions ([data.py](../../experiments/stl10_transfer/data.py#L162), [data.py](../../experiments/stl10_transfer/data.py#L176)). `verify` checks dataset identity (`STL-10` versus `STL-10 fixture`), config, seed, partition, preparation identity, source SHA-256s, the exact prepared-file manifest and every prepared-file hash ([data.py](../../experiments/stl10_transfer/data.py#L286)). It also reproduces public sampling and private partition IDs and validates IDs, capacities, and partition diagnostics ([data.py](../../experiments/stl10_transfer/data.py#L312)). The engine calls this verifier before opening the core reader ([engine.py](../../experiments/stl10_transfer/engine.py#L12)).
- **Train/test/unlabeled separation and labels:** private AE inputs come from `train_X.bin`; public features come from `unlabeled_X.bin`; test features and `test_y.bin` are held for evaluation ([data.py](../../experiments/stl10_transfer/data.py#L203), [data.py](../../experiments/stl10_transfer/data.py#L222), [data.py](../../experiments/stl10_transfer/data.py#L246)). Training labels are passed only to `partition_indices` to construct and record client allocation; they are not passed to AE, KMeans, or feature extraction ([data.py](../../experiments/stl10_transfer/data.py#L204), [data.py](../../experiments/stl10_transfer/data.py#L226)). Test labels are persisted separately and used by the shared `evaluate` function for Hungarian ACC, NMI, ARI, and predicted cluster counts ([data.py](../../experiments/stl10_transfer/data.py#L205), [public_scaling/engine.py](../../experiments/public_scaling/engine.py#L26)). This matches the preregistered label boundary.
- **Partition and M reuse:** the public pool is sampled once from the unlabeled asset using a seed-specific RNG; the full pool is feature-prepared and saved. `Config.preparation()` intentionally excludes `samples` and `degree`, so both M values share the same private IDs, AE, pseudo-labels, and prepared public prefix ([data.py](../../experiments/stl10_transfer/data.py#L222), [public_scaling/config.py](../../experiments/public_scaling/config.py#L49)). The public read slices the first `config.samples` rows; the runner passes the larger-M config during preparation. For IID, `partition_indices(..., public_pool=0, ...)` partitions the labeled train IDs without mixing them with the independent unlabeled file. For Dirichlet, it uses the same existing capacity-constrained partition function and records diagnostics.
- **STL image orientation and resize:** `read_images` reshapes STL-10 bytes to `(N,3,96,96)` and transposes the final two axes, matching torchvision STL-10's binary loading convention. `resize_area32` reshapes each channel into 32×3×32×3 cells and averages the two 3-pixel axes, then flattens RGB and scales to `[0,1]` ([data.py](../../experiments/stl10_transfer/data.py#L51), [data.py](../../experiments/stl10_transfer/data.py#L59)). Public images apply the same transpose before resize ([data.py](../../experiments/stl10_transfer/data.py#L224)). This implements the preregistered color-preserving, non-overlapping 3×3 mean pooling.
- **Preparation and cache cost:** preparation wall time begins before data verification/preparation and includes feature generation, KMeans and writes, with measured transfer time subtracted and recorded separately ([data.py](../../experiments/stl10_transfer/data.py#L177), [data.py](../../experiments/stl10_transfer/data.py#L279)). The engine's `with_shared_preparation_seconds` adds the recorded shared max-pool preparation, core load time, and full head pipeline ([engine.py](../../experiments/stl10_transfer/engine.py#L24), [engine.py](../../experiments/stl10_transfer/engine.py#L36)). This is consistent with charging the full shared preparation cost to either M and keeping download time separate. Cache hits verify the prepared bundle and reuse its original measured preparation time rather than reporting zero.
- **Training and timing reuse:** `WorkloadMethod` is the existing private-workload implementation, preserving private SGD, public student scheduling, exchange, and B/E/D generation logic. The STL engine runs one method and one full round sequence, sums initialization plus each round's `pipeline_seconds` for `head_pipeline_seconds`, and separately sums the phase timers ([engine.py](../../experiments/stl10_transfer/engine.py#L25), [engine.py](../../experiments/stl10_transfer/engine.py#L36)). `audit` and `evaluate` execute outside round pipeline timing and their elapsed times are recorded as excluded validation/evaluation time ([engine.py](../../experiments/stl10_transfer/engine.py#L31), [engine.py](../../experiments/stl10_transfer/engine.py#L34), [engine.py](../../experiments/stl10_transfer/engine.py#L48)). This matches the registered complete-head timer and the requirement that verification/audit not be included in it.
- **Quality and diagnostics:** shared `evaluate` reports each client's ACC/NMI/ARI, occupied clusters, largest cluster fraction, and cluster counts; `Coverage` records public scheduling/usage separately. The engine persists per-round metrics, coverage, traffic, and method array bytes. The selected final metric is the last evaluation round. This supports the registered requirement to retain per-client quality and cluster occupancy.

## Caveats for the formal run

1. I inspected but did not execute the downloader or verify a real archive. The curl fallback therefore remains operationally unverified; checksum validation is present after either download path.
2. `verify` checks source bytes against the SHA-256 values stored in the prepared metadata and checks that metadata claims the official checksum constants. It does not recompute each official member MD5 on every worker verification. The normal preparation path calls `ensure_data` first, which recomputes member MD5s; workers additionally verify source SHA-256 and the frozen prepared marker. This is sufficient for the current parent/worker flow, though adding member-MD5 recomputation inside standalone `verify` would make that helper stronger in isolation.
3. On cache hits, `prepare` calls `ensure_data` before it discovers the existing cache, so official source checksums are re-read. Those repeated validation passes are not added to the cached C0 preparation time; they are integrity-check overhead outside feature preparation and method timing. Keep them out of the reported model as currently specified, and avoid describing the runner's end-to-end wall time as C0.

No blocking issue identified in this review.
